# 三池子匹配结果编辑

适用 `/admin/matching/[id]`。自动匹配算法、评分、报名问卷和玩家结果格式保持不变；人工分组扩展及发布检查见下方「按时间人工分组」。

## 操作与边界

- 电脑端三个独立滚动区域：双人本、多人本、未匹配。姓名单击展开资料，双人按字段对齐；本人性别、搭档性别偏好和可用日期时段优先显示。
- 超级管理员使用打开页面时同一版本的当前报名摘要；普通管理员沿用档案与去敏权限。热力图仍使用原批输入。保存前任何当前输入变化均要求重新核对。
- 双人取消后两人留在双人池，灰线仅作为原关系提示；拖走一人不带走另一人。长按 350ms 拖动，也可以使用姓名菜单及勾选两人配对。建立配对先预览再确认。
- 尚未使用人工分组的原多人池唯一且固定共同日期时段。新成员必须满足该时段和完整组约束，不合条件者进入未匹配池。编辑中的一至两人临时池不能保存，须补足或移出，不能静默改成双人。
- 重新匹配只输入当前未匹配池，不包含双人池的等待人员。已有双人和多人池时间保持；调用既有自动算法，并尝试把符合完整组约束的剩余人员补入多人池。
- 编辑先暂存于当前页面，统一保存；撤销、放弃调整、离开提示均适用。手机只读，已发布结果须先沿既有流程撤回。锁定结果须解锁后调整。

## 保存与审计

`board-service.ts` 在服务端重新构造完整输入、核验人员范围、完整性、资格、锁定、时间和硬约束。客户端不提交可信评分。未修改的结果保留原行、编号、时间和分数。

`admin_save_matching_board` 仅服务端可调用。一次事务取消被替换的旧结果、插入新结果、更新未匹配诊断与计数、保存灰线和等待位置，并记录操作理由、原输入/source、engine 和回执。保存不通知玩家。数据库再次检查版本、共同时间、硬约束及人员守恒。原模式保留单池限制，人工分组模式允许多个成员不重叠的小组。

批次人员范围来自原运行输入及本批历史结果/诊断，后来仅新增报名的人不会自动混入。原问卷、面试评分和旧运行快照不变。

重复保存必须沿用同一操作 ID 和请求 SHA。网络中断保存到 sessionStorage 的只有操作参数和人员 ID，不包含问卷/互评。核对成功后重新读取权威快照及真实结果 UUID；读取失败继续保留原请求。不同内容不能复用已成功编号。

新增私有 schema `matching_board` 的 `state`、`operations`；无浏览器表读写权限。隐私处理清除相关输入、布局与审计敏感内容。旧调整记录和新统一保存记录均可查看。

## 姓名底色、快捷连接与个人锁

- 姓名背景只依据成员档案性别：女性浅粉、男性浅蓝、其他/未设置灰色；选中态用外圈，不覆盖性别底色。
- 外部 `&` 单击解除配对，灰色 `&` 单击经服务端兼容性检查后恢复；两种操作均进入待保存草稿，保持模块位置。恢复不跳过任何硬约束。
- 姓名旁的小锁将该成员固定在本批双人池。单锁仍可拆对、留在双人池等待、重新配对；不能移入多人或未匹配池。原有效配对两人均锁定时保留原配对，要拆对先解锁至少一人。已有整组锁独立保留。
- 个人锁与多人池锁均不需手写理由，系统记录操作人、时间和固定审计说明。锁立即保存，若页面有未保存的人员调整，先保存或撤销，再切换锁定。
- 个人锁原子操作使用明确目标状态、操作 UUID 和版本；响应中断、保存成功但重读失败、随后方案被发布等情况仍能用原请求核对，不重复反向切换。
- 多人池列出当前全员共同可用的日期与时段，当前安排优先，其余按日期和上午/下午/晚上排序，前3项标为推荐。该顺序是展示规则，并非新增时间评分或改变匹配算法；不足3项不虚构。完整个人问卷与交集继续遵守原管理员可见权限。
- 新迁移 `20261025170225_matching_board_member_locks.sql` 添加私有个人锁、独立锁审计、服务端RPC及数据库最终位置约束；单人锁不会被旧操作入口绕过，也不阻断既有发布、玩家取消与隐私擦除流程。


## 按时间人工分组

多人模块上下分区。上方保留尚未分组人员与入池共同时间；下方显示已确认小组和覆盖人数最多的前 5 个候选日期/时段。每个候选至少 3 人，人数相同时按日期、上午/下午/晚上排序。候选仅反映可用时间，确认及保存仍检查原匹配硬约束；不存在的第二、三或第五项不会补造。

候选行默认勾选该时段全部可用成员，同一人可在多个候选行重复出现。可取消勾选后确认一个子集，至少 3 人、不设人数上限。确认后该人移出上方池子和其他候选，只归属一个正式小组。时间在左、姓名在右，窄屏换行。姓名颜色、资料弹窗、350ms长按拖动沿用原界面；也可在资料菜单选择目标小组。候选间拖动只调整候选选择，确认后才建立正式组。

首次确认分组把本地草稿转为 `multiMode: grouped`，下方 `multiGroups` 是正式结果，上方 `multi` 仅是待分组名单，不带结果编号。保存时将原池取消为历史结果，逐组写入结果；布局记录 `waitingMultiIds` 与 `multiPoolSlot`。待分组可以剩 1～2 人并保存，正式组不足 3 人只能暂时编辑，须补足或移空才可保存。发布前待分组池必须清空，剩余人员需分组或明确移至未匹配池；服务器和数据库最终发布路径均检查。保存不发布、不通知。

原自动算法继续生成单池；已有单池尤其已发布的大于6人旧结果不会迁移或自动拆开。首次正式分组之前保留原单池行为，首次分组可在未保存时撤销，保存后的分组模式不能被旧页面降回单池。未匹配重跑仅处理该池，保留现有正式组，新多人候选进入上方等待。原多人池锁定时先解锁才能拆组；正式组逐组锁定，双人个人锁和整对锁保持原规则。

候选时段只对有原始报名可见权限的管理员显示。保存版本包含分组布局，旧调整入口在分组模式下拒绝新增/恢复写入并引导回三池页面，成功回执仍可读取。匿名化会清理待分组布局，保留其他人的位置。页面编辑状态读取失败时，以已有全部正式结果只读展示，不把第二组以后成员放入未匹配。

迁移 `20261027223546_matching_board_time_groups.sql` 只替换私有函数、增加私有校验，不创建新表、不回填业务数据。上线先核对依赖函数源码哈希和单条迁移 dry-run，应用后运行 `supabase/audits/matching-board-groups-postflight.sql` 并比较既有业务表摘要，再部署应用。旧代码不能读取新保存的多组结构，因此出现问题应优先修复前进；不能在已产生新分组后直接回退旧应用。

验证包括 `board-group-time-options.test.ts`、`MatchingBoardGroups.test.ts`、引擎与服务边界测试，以及 `supabase/audits/matching-board-groups-pglite.mjs` 的真实隔离 PostgreSQL 事务、权限、保存回执及发布分配检查。`node scripts/matching-groups/visual-review.mjs 3241` 提供虚构数据本地视觉验收，不连接线上数据库。既有三池、个人锁及发布回归仍须通过。

## 4–6人分组建议

中央多人模块顺序为：多人候选池／待分组人员、4–6人分组、按时间分组。未拆分的单池和下方普通时间组保留原规则。中间栏记录4–6人推荐类型，人工调整可超出该范围（至少3人），不按人数推断旧结果的类型。

有原始报名查看权限的管理员打开可编辑草稿时自动读取一次推荐。服务端仅使用上方未确认人员，以完整的日期及时段交集和现有群组硬约束筛选；不读取双人池或未匹配池作为推荐来源，不拆已确认组。方案内成员不重复，先尽量提高4–6人入组人数，再降低组间人数方差，最后优先较少组数：8人可分4+4，10人可分5+5，7人最多推荐6人并留下1人。算法为有计算预算的确定性搜索，不承诺任意复杂约束下的全局最优；单次推荐最多500人，超出时提示先分批处理。原自动匹配算法与评分不变。

推荐只是独立的页面编辑状态，确认前人员仍属于上方池，也仍可出现在下方时段候选。拖动推荐只修改建议，服务端检查移入目标组的共同时间与现有条件；确认正式分组时再核验完整分配。已有人员确认到任何正式组后，只从受影响的建议中移除，不重新安排其他人。人工调整不会自动重新生成；「重新推荐」主动重新计算当前尚未确认人员。异步响应若对应旧的草稿或版本则丢弃，避免覆盖更新后的操作。

通过中间栏确认的组继续留在中间，显示全部共同时间并突出推荐安排。自动建议保持4–6人；管理员调整后允许3人、7人等小组，超出推荐人数只提示，少于3人时须补足或解散后才能保存、发布。未确认建议不占用正式分配。确认后仍由「保存调整」统一持久化，保存不发布、不发送通知。手机可查看建议及正式组，调整仍沿用电脑端规则。现有小组锁、已发布只读、权限和待分组发布检查继续有效。

`BoardMulti.groupKind: small` 通过既有布局中的 `smallGroupMemberIds` 完整成员集合保存，数据库验证每个标记精确对应唯一有效多人结果，且系统推荐人数为4–6；`manualSmallGroupMemberIds` 精确标记人工调整小组并允许至少3人。已存在小组标记时旧客户端不能省略字段，保留的结果不能去掉标记降级；新客户端解散全部小组时显式传空数组。取消、隐私清理按原流程处理，布局不保留已失效成员集合。新迁移 `20261030103412_matching_board_small_groups.sql` 仅安装函数与校验，不改写现有结果；部署前运行 `matching-board-small-groups-pglite.mjs` 与旧三池、锁、时间组审计，先应用本条迁移再部署代码。

## 发布前结果确认与Excel一致性

三个池子下方的「发布前结果确认」只展示已保存的有效结果，每对或每组一行，包含稳定组号、人数、完整成员、推荐时间、其他共同时间。默认每次显示20组，支持全部／双人／多人筛选、姓名或会员编号搜索和共同时间展开；待双人搭档、待多人分组与未匹配分别列出。原多人池在尚未确认拆分时仍显示为一个已保存多人组，推荐建议不会混入核对结果。

`fetchMatchingBoard` 在原 `admin_get_matching_board` 同次只读capture上组装 `savedReview`，不额外创建结果或数据库记录。姓名、编号、当前未取消的报名时间均来自该次capture；仅输出必要DTO，完整共同时间仍限定原始报名查看权限。匿名化成员的残留身份、时间、备注不可从历史资料恢复；缺失、重复或不合法时间标记为资料不可用，不伪造共同时间。

有未保存调整、保存待确认、锁定待确认或需重新载入状态时隐藏旧核对表，并阻止导出／发布。保存、发布、撤回成功后重新读取当前板面，刷新核对区。发布传输中断、服务端结果未知或成功后的重读失败同样隐藏旧表，要求只读核对，不自动重复操作。顶部「查看发布前结果」可定位到核对区。

所有收集时间匹配的Excel导出复用 `readSavedMatchingReview`，直接消费相同DTO中的分组、成员、推荐时间与当前共同时间，不再用最初运行快照重算时间。保留四个sheet及原有列顺序，末尾补组号、人数、分组方式、安排状态和核对版本；第三表明确区分待搭档／待分组／未匹配，第四表标明已保存草稿或已发布，不能将sheet名称视为发布回执。无轮次或非matching用途的历史导出仍沿用原路径。

网页下载携带 `revision` 和 `signature`，服务器重读后不一致返回409，不下载另一版方案；客户端不会把登录页或错误JSON保存为Excel。匹配页面的「确认发布」同时提交完整板面版本与核对内容签名：取得原发布准备数据后重新比较完整板面版本，并验证当前已保存组员／推荐时间／共同时间的签名，随后沿用原授权证明和原子发布最终检查。发布不会重匹配或重评分，原通知及幂等规则保持。撤回后结果行版本归零，但会话发布版本保留；草稿发布必须使用会话版本，不能从结果行推断。

本增量没有数据库迁移，不修改活动、问卷、报名、算法或玩家页面。用 `session-review*`、导出route及三池UI测试验证读取与并发边界；`supabase/audits/matching-saved-review-pglite.mjs` 在隔离虚构数据上核对真实board／publication capture、XLSX及发布前后逐组一致性。生产验收仅查看既有测试批次和下载已保存结果，禁止为验收确认、保存、撤回、发布真实活动。

### 导出的本人性别与未匹配原因

报名CSV及匹配Excel各表在既有列末尾追加「玩家性别」，保留原列顺序。本人性别来自当前 `member_identity.gender`，映射为男／女／其他／未填写；不使用搭档性别偏好或历史导入资料推断。Excel多人或双人行以「姓名：性别」逐行对应，未匹配行直接显示该人的性别。已匿名化成员不补回残留性别。

Excel「未匹配名单」另有「未匹配成功原因」。优先反映已保存的待搭档／待分组布局；其余人员只使用本批保存的诊断，区分人工调整与算法记录。限额搜索的未分配不解释为不存在可行组合，历史中文记录注明历史来源，缺失或无效诊断明确标记无法判断；多条不同诊断全部保留并提示核对。报名留言仍在备注列，不作为未匹配原因。

诊断只在超级管理员下载Excel时读取，限定当前批次及当前未分配的非匿名化成员，按ID排序并核对精确记录数，防止截断被当作缺失。读取后再次核对完整板面版本（已包含诊断与当前资料），版本变化、读失败或记录不完整时停止导出。公开的后台确认表DTO、发布签名、玩家端及数据库结构均不改变。


## 人工建组与工作人员留言

`4–6人分组`与`按时间分组`均可手动建组，从本批多人候选、未匹配成员中选择，再选择该小组全员共同时间。已有搭档或正式小组的人员须先移出原关系。推荐仍严格4–6人；管理员修改推荐或正式小组后，明确保存人工标记，允许至少3人，超出4–6只提示。锁定、报名类型、性别倾向、回避关系和当前资格继续校验。正式小组可修改推荐时间、解散到多人待分组区；确认后保持可见，所有变更统一保存。

分组模式中的上方待分组区属于未分配候选集合，可以包含不同时间的人员；全员共同时间只对具体正式组校验。原未拆分的单一多人池继续沿用原固定时间规则。待多人分组人员仍阻止发布。

未匹配池可填写300字以内的选填工作人员留言，独立于内部操作理由与诊断。编辑和保存均不发通知。核对表显示全文及最终可接收名单（含符合条件的等待双人搭档，排除历史已取消、失效账号及其他批次已有有效匹配者）；Excel未匹配名单导出相同留言，待多人分组及注销人员不导出。发布签名绑定留言，最终发布事务冻结对应版本，只向该版本未匹配玩家展示；空留言和历史结果不显示额外区域。小铃铛简短通知保持现有文案。

## CSV批量人工调整

匹配详情顶部的「下载调整模板CSV」「上传人工调整CSV」仅供可编辑草稿的超级管理员使用；页面有未保存调整、保存／锁定结果待确认或需重读时禁用。模板来自当前已保存批次，每位玩家一行，完整保留人员标识、会员编号、姓名、本人性别和当前安排。系统列绑定批次、版本及参考信息；签名使用已有服务端凭据作分域HMAC，不新增环境变量或表，不将凭据写入文件或客户端。

可编辑目标池（双人／多人／未匹配）、组号、多人分组栏、推荐日期及时段。同组使用相同组号和共同时间；双人恰好2人，多人至少3人，4–6为推荐范围。多人组可显示在「4–6人分组」或「按时间分组」。双人／多人无组号为等待搭档／待分组，不填时间；未匹配不填组号、分组栏和时间。日期使用`YYYY-MM-DD`；兼容Excel另存后的明确`YYYY/M/D`格式并提示统一转换，拒绝月日在前、两位年份、日期序号和公式。时段为上午、下午或晚上。参考字段不用于更改成员档案或报名，遗漏、重复、批次外人员、改动系统列或混用旧模板会阻止整份应用。

上传UTF-8 CSV后先显示校验错误、人数比较及逐人调整前后差异，支持超过25人时逐批展开。点击「应用到编辑草稿」会再次只读获取当前批次、复核版本及文件，再把完整方案交给现有页面编辑；不会上传到文件存储、写入业务数据、发布或通知。可一次撤销整次导入、放弃或继续调整，最后仍由管理员填写操作理由并手动保存。保存、Excel核对和正式发布继续复用现有原子流程。

未改变的配对、小组保留结果编号、评分和锁定；仅改组号或行顺序视为无变化，旧单池无变化时保留原结构。CSV手动指定的有效双人共同时间使用临时`manuallyScheduled`标记，在现有保存服务中核验并保留；保存后时间属于结果行，不新增布局字段或迁移。工作人员留言不在CSV中编辑，始终保留当前已保存值；旧灰线中仍共同等待搭档的成员保留提示。当前资格、报名类型、性别倾向、回避关系、个人锁与整组锁继续由服务端和数据库复核。

文件限1.5MB，采用带BOM、CRLF及标准引号的CSV，参考字段防止Excel公式执行。下载拒绝登录HTML和错误响应，CSV只读请求不创建后台操作记录。`board-csv*`测试与`supabase/audits/matching-board-csv-pglite.mjs`以虚构数据验证完整导入、手选时间、人数、锁、并发及保存一致性。本功能无需数据库迁移。真实活动验收只读核对入口和数据摘要，不上传、应用、保存或发布真实方案。
