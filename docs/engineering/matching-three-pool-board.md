# 三池子匹配结果编辑

适用 `/admin/matching/[id]`。自动匹配算法、评分、报名问卷、玩家结果和发布规则保持不变。

## 操作与边界

- 电脑端三个独立滚动区域：双人本、多人本、未匹配。姓名单击展开资料，双人按字段对齐；本人性别、搭档性别偏好和可用日期时段优先显示。
- 超级管理员使用打开页面时同一版本的当前报名摘要；普通管理员沿用档案与去敏权限。热力图仍使用原批输入。保存前任何当前输入变化均要求重新核对。
- 双人取消后两人留在双人池，灰线仅作为原关系提示；拖走一人不带走另一人。长按 350ms 拖动，也可以使用姓名菜单及勾选两人配对。建立配对先预览再确认。
- 多人池唯一且固定共同日期时段。新成员必须满足该时段和完整组约束，不合条件者进入未匹配池。编辑中的一至两人临时池不能保存，须补足或移出，不能静默改成双人。
- 重新匹配只输入当前未匹配池，不包含双人池的等待人员。已有双人和多人池时间保持；调用既有自动算法，并尝试把符合完整组约束的剩余人员补入多人池。
- 编辑先暂存于当前页面，统一保存；撤销、放弃调整、离开提示均适用。手机只读，已发布结果须先沿既有流程撤回。锁定结果须解锁后调整。

## 保存与审计

`board-service.ts` 在服务端重新构造完整输入、核验人员范围、完整性、资格、锁定、时间和硬约束。客户端不提交可信评分。未修改的结果保留原行、编号、时间和分数。

`admin_save_matching_board` 仅服务端可调用。一次事务取消被替换的旧结果、插入新结果、更新未匹配诊断与计数、保存灰线和等待位置，并记录操作理由、原输入/source、engine 和回执。保存不通知玩家。数据库再次检查版本、共同时间、硬约束、唯一多人池及人员守恒。

批次人员范围来自原运行输入及本批历史结果/诊断，后来仅新增报名的人不会自动混入。原问卷、面试评分和旧运行快照不变。

重复保存必须沿用同一操作 ID 和请求 SHA。网络中断保存到 sessionStorage 的只有操作参数和人员 ID，不包含问卷/互评。核对成功后重新读取权威快照及真实结果 UUID；读取失败继续保留原请求。不同内容不能复用已成功编号。

新增私有 schema `matching_board` 的 `state`、`operations`；无浏览器表读写权限。隐私处理清除相关输入、布局与审计敏感内容。旧调整记录和新统一保存记录均可查看。
