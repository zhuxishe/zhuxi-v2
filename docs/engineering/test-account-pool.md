# 可登录测试账号池

用于正式站手机验收的27个独立测试账号，编号TST_001至TST_027。正式ZXS编号、问卷模板、算法权重和硬约束保持原规则。

## 身份和数据隔离

- `members.is_test` 由受保护的 `private.test_accounts` 登记支持，不能通过普通资料保存或编号编辑把真实会员改为测试账号。
- TST编号不进入正式ZXS编号标准化、分配序列或最高已发号计算。普通身份不能占用TST号。
- 正式会员人数、目录和相关统计默认排除测试身份；数据库仍保存27条新测试成员记录及27个新Auth账号。本次同时删除27条旧临时成员记录，因此成员表总行数不能用来判断正式会员人数。
- `match_rounds.is_test` 配合精确成员白名单。测试账号不能报名正式轮次。默认仅名单内会员可报名、发现或接收该测试轮次结果；单独开启「所有正常正式玩家」的轮次按下方范围设置执行。
- 配对历史、互评与后续评分按测试/正式轮次分域，测试数据不改变真实会员的正式评分或成长统计。
- 测试匹配仍经过原资格、共同时间、黑名单、类型与性别偏好等校验；不新增强制发布或放宽资格的入口。

## 发布顺序

1. 先在隔离库验证迁移、权限、序列、统计、历史隔离及固定旧数据清理。
2. 只将三份新增迁移应用到核对过的Production项目，部署对应应用；不要重放历史迁移。
3. 用私密manifest准备新Auth身份和问卷答案。真实Auth Admin API创建登录账号，受控provision创建pending测试成员；真实面试前信息表提交后批准，再提交其余三类通用问卷。
4. 对旧27个临时测试成员执行只读预检，再单独执行受控清理。只有固定UUID、原导入批次、姓名编号和无发布/通知/其他业务引用全部匹配时才允许清理。删除相关旧草稿，不删除轮次或真实6人答卷；审计仅保留必要主体与删除事实。
5. 将原测试轮次配置为27个TST账号加ZXS_000、ZXS_001、ZXS_006、ZXS_016、ZXS_081、ZXS_250的精确白名单，然后由各TST账号通过原报名RPC报名。
6. 独立只读核对27个登录、4类问卷、33份报名、正式人数/编号与真实资料保护摘要。此流程不发布匹配结果。

操作入口为 `scripts/operations/test-account-pool/manage.mjs`，分阶段、可恢复，详见同目录README。账号manifest、密码、API密钥和保护基线必须保存在仓库外，权限0600，不得提交Git。

## 手动验收

使用正式站邮箱密码登录，测试邮箱使用不可投递的example.invalid保留域。密码找回邮件不可达，需要超级管理员受控维护。管理员在原测试轮次运行匹配，核对名单后手动发布；测试完成可撤回发布。

测试账号有真实登录身份，但不能交给真实会员用于真实活动。清理Auth和业务数据、释放身份都应通过单独预检和明确范围完成，不能按编号或昵称模糊删除。

本批授权真实成员共6人，全部保留真实身份、资料和原报名；仅该轮次被标记测试域，不把这6人标成测试账号。ZXS_083既有报名回执保留，不在本批参与或新通知名单中。

手工编辑全局黑名单、会员评分和活动出勤仍按正式规则生效。使用真实账号验收时，应限定在本测试轮次的匹配、通知和轮内互评，不要以这些全局编辑器测试隔离效果。

## API权限实现

`20261025061614_isolate_test_pool_access_helpers.sql` 仅移动两项权限检查实现至非API `test_pool_access` schema，保留原OID/ACL/owner/search_path和RLS依赖。public/private同名入口为SECURITY INVOKER；匿名及登录用户不能通过API直接调用definer实现。该收尾不改变可见范围或匹配规则。


## 按轮次开放给正常正式玩家

`20261028134535_test_round_formal_player_access.sql` 仅安装能力，不自动开启任何轮次。设置和审计位于非 API schema `test_pool_access`，无公开管理接口或浏览器表权限。原名单始终有效，开启目标轮次后再额外允许 `is_test=false`、已审核、active、current、player、已绑定账号且未匿名化的正式成员；后续新满足条件的账号同样有效。TST仍须原名单，其他测试轮次默认名单制。身份、历史/互评统计分域和原报名资料检查不变。

在独立预检和明确授权后，数据库操作者使用 `test_pool_access.set_round_formal_player_access(round_id, enabled, reason, operation_id)`。该 SECURITY INVOKER 函数无 anon/authenticated/service_role EXECUTE，仅数据库所有者可使用；记录真实 `session_user`/`current_user`，不假冒应用管理员。操作号与完整参数相同的重试返回原回执，改变内容则拒绝。审计表拒绝UPDATE、DELETE与TRUNCATE。

仅更改指定轮次的设置，不批量重写成员白名单，不创建报名、匹配、发布或通知。报名窗口仍由原状态、截止时间和提交保护控制；范围谓词不绑定截止时间，确保关闭收集后原参与者还能查看结果。既有结果与答卷仍受本人权限控制，开放轮次不等于开放别人的资料。

旧固定33人配置入口会在取得同一轮次锁后检查动态模式，开启时拒绝重配。若想关闭动态模式，任何名单外报名（包括取消记录）、结果（包括历史取消结果）、未匹配诊断、发布名册（即使原会话已删除）或互评名单都将阻止直接关闭；须另行制定保留历史访问的方案，不能删除参与记录来回退。尚无这些记录时可通过新的操作号关闭，并保留审计。

验证：`test-round-formal-access-pglite.mjs` 复用原152项测试账号池回归，覆盖实际权限、报名RLS、身份边界、新账号动态准入、截止后历史可见、模式切换保护、幂等和不可变审计。生产只读结构核对使用 `test-round-formal-access-postflight.sql`；开启前后分别比对问卷、报名、结果、发布、通知及原白名单摘要。


## 后台参与范围管理

`20261028163133_round_audience_admin.sql` 安装后台只读快照、超级管理员原子保存和本人操作回执 RPC，不修改现有范围或名单。公开入口是 `SECURITY INVOKER`，受控实现位于非 API 的 `test_pool_access`；普通管理员只能查看，保存要求当前认证用户仍为有效超级管理员。客户端不能提供操作者身份，数据库锁定管理员后再次验证，并记录真实管理员与账号 ID。

后台入口为「匹配管理 → 轮次详情 → 内容、问卷与预览 → 参与范围」。活动属性只读；正式轮次默认正常正式玩家范围，不在此转换为测试。测试匹配轮次可以切换指定名单/所有正常正式玩家，搜索姓名或会员编号调整名单。显示人数只代表账号及范围资格，不代表三项报名资料已完成。

已有参与记录的名单成员不能移除；切回指定名单前必须把所有历史参与者纳入所选名单，包括取消答卷、取消结果、未匹配诊断、原会话已删除的发布名册及互评名单。可以在一次保存中添加这些人员并收窄范围，原运维 setter 再复核历史保护。名单与模式在同一事务保存，不创建报名、匹配、发布或通知。

保存携带完整名单、范围、理由、版本和操作编号。版本涵盖活动配置、范围设置、明确名单、历史参与者及已提交操作数；运维侧更新和旧名单重配也使旧页面失效。未知结果按同一操作号查询本人回执；管理员后来降级为普通管理员仍可读取本人已经提交的回执，但不能再写。失去管理员身份或账号停用会失去读取权限。操作审计不允许 UPDATE、DELETE 或 TRUNCATE。

本地真实 SQL 检查使用 `supabase/audits/round-audience-admin-pglite.mjs`，复用原测试池及开放范围用例；部署后用 `supabase/audits/round-audience-admin-postflight.sql` 验证最小权限、旧范围规则保留和审计保护。生产验收只读查看现有设置，不为测试 UI 修改真实范围或名单。
