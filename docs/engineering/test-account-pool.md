# 可登录测试账号池

用于正式站手机验收的27个独立测试账号，编号TST_001至TST_027。正式ZXS编号、问卷模板、算法权重和硬约束保持原规则。

## 身份和数据隔离

- `members.is_test` 由受保护的 `private.test_accounts` 登记支持，不能通过普通资料保存或编号编辑把真实会员改为测试账号。
- TST编号不进入正式ZXS编号标准化、分配序列或最高已发号计算。普通身份不能占用TST号。
- 正式会员人数、目录和相关统计默认排除测试身份；数据库仍保存27条新测试成员记录及27个新Auth账号。本次同时删除27条旧临时成员记录，因此成员表总行数不能用来判断正式会员人数。
- `match_rounds.is_test` 配合精确成员白名单。测试账号不能报名正式轮次，名单外会员不能报名、发现或接收该测试轮次结果。
- 配对历史、互评与后续评分按测试/正式轮次分域，测试数据不改变真实会员的正式评分或成长统计。
- 测试匹配仍经过原资格、共同时间、黑名单、类型与性别偏好等校验；不新增强制发布或放宽资格的入口。

## 发布顺序

1. 先在隔离库验证迁移、权限、序列、统计、历史隔离及固定旧数据清理。
2. 只将三份新增迁移应用到核对过的Production项目，部署对应应用；不要重放历史迁移。
3. 用私密manifest准备新Auth身份和问卷答案。真实Auth Admin API创建登录账号，受控provision创建pending测试成员；真实面试前信息表提交后批准，再提交其余三类通用问卷。
4. 对旧27个临时测试成员执行只读预检，再单独执行受控清理。只有固定UUID、原导入批次、姓名编号和无发布/通知/其他业务引用全部匹配时才允许清理。删除相关旧草稿，不删除轮次或真实6人答卷；审计仅保留必要主体与删除事实。
5. 将原测试轮次配置为27个TST账号加ZXS_000、ZXS_001、ZXS_006、ZXS_016、ZXS_081、ZXS_250的精确白名单，然后由各TST账号通过原报名RPC报名。
6. 独立只读核对27个登录、4类问卷、33份报名、正式人数/编号与真实资料保护摘要。此流程不发布匹配结果。

操作入口为 `scripts/operations/test-account-pool/manage.mjs`，分阶段、可恢复，详见同目录README。账号manifest、密码、API密钥和保护基线必须保存在仓库外，权限0600，不得提交Git。

## 手动验收

使用正式站邮箱密码登录，测试邮箱使用不可投递的example.invalid保留域。密码找回邮件不可达，需要超级管理员受控维护。管理员在原测试轮次运行匹配，核对名单后手动发布；测试完成可撤回发布。

测试账号有真实登录身份，但不能交给真实会员用于真实活动。清理Auth和业务数据、释放身份都应通过单独预检和明确范围完成，不能按编号或昵称模糊删除。

本批授权真实成员共6人，全部保留真实身份、资料和原报名；仅该轮次被标记测试域，不把这6人标成测试账号。ZXS_083既有报名回执保留，不在本批参与或新通知名单中。

手工编辑全局黑名单、会员评分和活动出勤仍按正式规则生效。使用真实账号验收时，应限定在本测试轮次的匹配、通知和轮内互评，不要以这些全局编辑器测试隔离效果。
